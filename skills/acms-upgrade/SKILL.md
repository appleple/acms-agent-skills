# a-blog cms のバージョンアップ

## 移行先ごとのファイル

| 移行先 | 移行元 | 読むファイル | チェック定義 |
|---|---|---|---|
| Ver. 3.2 | Ver. 3.1.x | references/to-3.2.md | scripts/checks/to-3.2.tsv |

移行先を足すときは references/_template.md を写して `to-<版>.md` と `scripts/checks/to-<版>.tsv` を作り、この表に 1 行足す。

## 手順

### 1. 現在のバージョンを判定する

acms-project-triage の `scripts/detect.sh` で版を判定する。3.2 未満のサイトでは「対象外」の warning が出るが、このスキルはその版を扱うので続けてよい。版が「不明」なら推測せず、利用者に管理画面で確かめてもらう。

### 2. 移行先を決める

- 移行先は、その系列の最新のパッチ版にする（3.2 なら 3.2.x の最新）。パッチ版でも本体の挙動が変わることがあるので、決めた版の番号を利用者と共有する。
- 2 つ以上の版を飛び越えるとき（3.0 から 3.2 など）は、途中の版の移行内容もすべて読む。上の表にない版（3.0 → 3.1 など）は、公式の移行ガイド（[Ver. 3.0.x から 3.1.x](https://developer.a-blogcms.jp/document/migration/301x/)、[Ver. 2.11.x から 3.0.x](https://developer.a-blogcms.jp/document/migration/300x/)）を読み、scan.sh ではその版の変更を見つけられないと利用者に伝える。
- 要件（PHP・MySQL）を `references/to-<版>.md` の「前提」で確かめる。サーバーの PHP を上げる必要があるなら、どの順で上げるかを利用者とサーバーの管理者に決めてもらう。

### 3. バックアップを取る

- データベースと、設置ディレクトリのファイル全体（`themes/`・`extension/`・`archives/`・`media/`・`storage/`・`private/`・`config.server.php`・`.env`・`license.php` を含む）の両方を取る。
- オンラインアップデートは置き換えるシステムファイルを `private/backup<日時>/` に退避するが、データベースはバックアップしない。マイナーバージョンアップの DB 更新ではデータの変換が走ることがあり、元に戻すには DB のバックアップが要る。
- DB のダンプやサーバー上のコピーは、利用者（またはサーバーの管理者）に実行してもらう。エージェントは接続情報を知るために `config.server.php`・`.env`・`private/` を開かない。

### 4. 検証環境で先に試す

本番のファイルと DB を複製した検証環境で、手順 5〜8 を先に通す。本番でいきなり本体を更新しない。検証環境がなければ用意を頼み、用意できないなら、そのリスク（表示崩れ・ロールバックに DB の復元が要る）を伝えてから利用者に判断してもらう。

### 5. 要修正箇所を洗い出す

更新前のサイト（検証環境）に対して実行する。パスは、このスキルのディレクトリからの相対パス。

```sh
sh scripts/scan.sh <設置ディレクトリ> <移行先の版（例 3.2）>
```

- 版を飛び越えるときは、表にある途中の版ごとに実行する。チェック定義のない版を渡すと、ある版の一覧を出して終了コード 2 で終わる。
- 出力はチェックごとに「ID・件数・何が問題か・references の見出し・該当ファイル:行」。検出は文字列の一致による候補なので、直す前に該当行を開いて確かめる。`要確認` で始まるものは見比べる箇所。
- 最後の節は、テーマで `themes/system` と同じパスに置いたファイル（上書き）の一覧。本体の更新後に、新しい system の同じファイルと見比べる。
- scan.sh が読むのは `themes/`（system を除く）と `extension/` だけ。`config.server.php` と `private/` は読まない。

### 6. テーマとプラグイン（拡張アプリ）を直す

`references/to-<版>.md` の「テーマで直すこと」「プラグイン（拡張アプリ）で直すこと」の順に直す。各チェック ID の直し方と根拠は同じファイルの「下位互換性のない変更」「非推奨になった機能と代替」の表にある。

- 移行元の版のままで直せるもの（代替のモジュールが移行元にもある、廃止された記述を外す）は、本体を更新する前に直す。旧版の `themes/system` から取っておくもの（旧 `acms.css` など）も更新前に取る。
- `themes/system/`・`php/`・`js/` は直さない。本体の更新で上書きされるため。直すのはテーマ・`extension/`・設定。
- 配布されているプラグインは、移行先の版に対応した版が出ているかを先に確かめる。

### 7. 本体をアップデートする

手順そのものは公式のページに従う。ここでは選び方だけを示す。

| 方法 | 使うとき | 公式の手順 |
|---|---|---|
| オンラインアップデート（管理画面 > 更新） | マイナーバージョンアップ（3.1 → 3.2 など）。管理画面 > コンフィグ > 機能設定で「マイナーバージョンも含める」にする。ファイルの置き換えと DB の更新をまとめて行う | [オンラインアップデート](https://developer.a-blogcms.jp/document/update/online-update.html) |
| 簡単アップデート（`update.php`） | オンラインアップデートが使えないとき、メジャーバージョンアップ（2.x → 3.0 など） | [簡単アップデート（手動）](https://developer.a-blogcms.jp/document/update/update-yourself.html) |
| 手動アップデート（FTP などで上書き） | 上の 2 つが使えないとき。上書きしないファイル・フォルダに注意する | [手動アップデート](https://developer.a-blogcms.jp/document/update/update-yourself-all.html) |

- 手動の 2 つでは、ファイルを置いた後にメンテナンス画面（または管理画面 > 更新）から DB を更新し、`setup` ディレクトリを推測されにくい名前に変える。DB の更新を忘れると、ファイルと DB の版が合わないまま動く。
- 更新の実行は、本番・検証のどちらでも利用者の了承を得てから行う。

### 8. 確認する

- `references/to-<版>.md` の「移行後の確認」を順に見る。
- 管理画面のユーザー設定でデバッグモードにすると、非推奨の機能を使った箇所が監査ログ（PHP 側）とブラウザーのコンソール（組み込み JS）に出る。
- scan.sh をもう一度実行し、`要確認` 以外の検出が 0 件になったことを確かめる。

### 9. 本番に反映する

検証環境で確認が済んだら、本番で手順 3（バックアップ）→ 6 の修正の反映 → 7 → 8 を行う。作業中はサイトが正しく表示されない時間があるので、時間帯を利用者と決める。問題が出たときに戻す手順（ファイルと DB の復元）を先に決めておく。

## 守ること

- `config.server.php`・`.env`・`private/` 配下は開かない。DB の接続情報や API キー・秘密鍵があるため。`private/config.system.yaml` に設定を足す必要があるときは、足す行を示して利用者に書いてもらう。
- 版を推測で決めない。移行元と移行先の版を確かめてから直す内容を決める。
- 公式の移行ガイドにない変更を見つけたとき（本体のソースで消えているなど）は、根拠を示して利用者に伝える。確かめられない挙動は「未確認」と伝える。
