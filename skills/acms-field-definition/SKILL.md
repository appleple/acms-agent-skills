# a-blog cms のカスタムフィールド定義（Ver. 3.3 以降）

Ver. 3.3 で、カスタムフィールドの入力欄を HTML を書かずに定義できるようになった。定義は「値の説明書き」で、値は従来どおりカスタムフィールドとして保存される。そのため**出力の記法は従来のカスタムフィールドと同じ**で、定義を消しても値は消えない。

この内容は Ver. 3.3.0-alpha.1 のソースで確かめた。公式ドキュメント（developer.a-blogcms.jp）が公開されたら、そちらを正とする。

## 最初に確かめること

1. `acms-project-triage` でバージョンを判定する。**Ver. 3.3 未満なら、このスキルを使わず acms-custom-field（field.html で入力欄を書く方法）を使う。** 3.2 のサイトに定義の JSON や管理画面の手順を案内しても動かないため。
2. 変更する前に、既にある定義と値を確かめる。管理画面「フィールド定義」（対象ごとのタブ）で、既存のフィールドセット・使用中のフィールドの集計・定義の無い値（孤児値）を見る。既にあるキーを再利用できるなら新しく作らない。同じ意味の値が別のキーに分かれると、出力・検索・移行がすべて二重になるため。
3. テーマの `admin/entry/field.html` などに従来の入力欄があるかを確かめる（下の「従来の field.html との関係」）。

## 1. どこで定義するか

| 状況 | 定義する場所 |
|---|---|
| そのサイトだけで、運用者が後から項目を足し・直す | 管理画面「フィールド定義」（GUI） |
| テーマと一緒に配布する・複数のサイトで同じ定義を使う・定義を Git で管理する | テーマの `admin/field-definitions/<対象>.json`（references/theme-declaration.md） |
| 定義の型にない入力欄（独自の UI、複雑な連動）が要る | 従来の `field.html`（acms-custom-field）か、独自の型（テーマの `admin/field-types/`、プラグインの登録） |
| 子ブログにも同じ定義を使わせる | フィールドセットの scope を `global` にする（子ブログでは編集できず「使わない」にだけできる） |

- 対象は entry・category・blog・user・module の 5 つと、どの対象からも使い回す部品の `component`。ユニット・メディア・フォームには付けられない。
- GUI で作った定義はエクスポートした JSON をそのままテーマの宣言ファイルにできる。まず GUI で作って確かめ、配布するならエクスポートしてテーマに置く、の順が確実。

## 2. 型と名前を決める

- 型の選び方は references/field-types.md の判断表で決める。迷いやすいのは次の 3 つ。
  - 画像・PDF は `media-image`・`media-file`（メディア管理の ID を参照する）。`image`・`file`（アーカイブ）はユーザーの定義でしか選べない。
  - 他のエントリー・カテゴリー・ユーザーを指すなら、ID を text に入れず参照型（`relation-*`）にする。公開側で見えない参照先が出力から自動で外れ、参照先のタイトルや URL が補われるため。
  - 見た目のための項目（余白・文字色など）を作らない。表示の違いは `select` の「種類」（例: `layout_variant`）で表し、見た目はテンプレートで決める。
- キーは英字かアンダースコアで始まる英数字とアンダースコア（64 文字まで）。ハイフンは使えない。新規作成では接頭辞 `cf_` が最初から入る（システム設定 `field_definition_key_prefix`）。サイトに既存の命名規則があればそちらに合わせる。
- `title`・`status`・`code`・`link`・`date`・`page`・`tag`・`keyword` などの予約語と、`ACMS_POST` で始まる名前はキーにできない。
- 同じ役割の項目は、対象が違っても同じキーにする（例: エントリーとカテゴリーの OGP 画像をどちらも `ogp_image`）。テンプレートの部品を使い回せるため。

## 3. 必須と入力チェック

- 必須は `none`・`save`（保存時）・`publish`（公開時）から選ぶ。下書きの途中保存を止めたくない項目は `publish` にする。
- 必須と入力チェックはサーバー側で必ず強制され、公開ボタン・一覧の一括変更・CSV インポートでも効く。画面に入力欄が出ていなくても効く（下の「よくある誤り」）。
- `number`・`email`・`url`・日付などは型そのものの検査が掛かるので、同じ意味の入力チェックを重ねない。
- 条件付き表示で隠れている項目には、必須も入力チェックも掛からない。「オンラインのときだけ配信 URL を必須」は、配信 URL に開催形式の条件と必須の両方を設定すれば実現できる。

## 4. 変更が既存の値に与える影響

定義の変更は値を書き換えない（キーの変更だけが例外）。本番で変える前に、検証環境か定義のエクスポートで戻せる状態を作る。

| 変更 | 既存の値 | すること |
|---|---|---|
| キーの変更 | 管理画面のキーの変更は、保存済みの値も一括で書き換える（影響件数を確かめてから実行できる） | テンプレートの `{旧キー}`・`fields.旧キー` をテーマ全体で探して直す |
| 定義の削除・「使わない」 | 値は残り、孤児値として一覧に出る | 出力を止めるならテンプレートも直す。値も消すなら利用者に確認してから |
| 型の変更 | 値は変換されない。形の違う型（テキスト → 参照型、アーカイブ画像 → メディアなど）では読めなくなる | **中身のある項目の型は変えず、新しいキーの項目を足して値を移し、古い項目を「使わない」にする**。値の移し方は、件数が多ければ REST API（acms-rest-api。`fields` の PATCH）かエントリーの CSV のエクスポートとインポート、少なければ管理画面で手で入れ直す |
| テーマの切り替え | テーマで宣言した定義が消え、値は孤児値として残る | 新しいテーマにも同じ宣言ファイルを置く |
| 選択肢の value の変更 | 保存済みの value は変わらない | value は変えず label だけを直す。value を変えるなら値の移し替えを計画する |

## 5. 従来の field.html との関係

- 両方を同時に使える。既存サイトは何も直さなくても動き、field.html から定義への移行は必須ではない。
- **同じキーが field.html と定義の両方にあれば field.html が優先**され、定義側の入力欄は出ない。移すときは、定義を作ってから field.html の該当の入力欄を消す。
- テンプレート方式の画像・ファイル（アーカイブ）、リッチエディター、ライトエディター、テーブルの値を定義の型に移すツールは無い。メディア型に移すと `@path` などの派生キーが次の保存で消える。移す前に値の扱いを利用者と決める。
- テーマが `admin/entry/edit.html`・`admin/_layouts/entry/edit.html` などの編集画面を上書きしていると、定義の入力欄が出ない（system の編集画面にある定義の表示部分が無いため）。それでも必須は強制されるので、画面に無い必須項目のせいで保存できなくなる。上書きをやめるか、system の該当箇所を取り込む。

## 6. 出力する

- 記法は従来のカスタムフィールドと同じ。標準テンプレートは `{キー}`、Twig は `fields.キー.value`。メディア・グループ・画像の判定などの決まりは acms-custom-field の「出力する」に従う。
- 選択系は label ではなく value が出る。表示名が要るならテンプレートで value から決める。
- 参照型の出力（`{キー@title}`・`{キー@url}` など、Twig での参照先のカスタムフィールドの展開）は references/field-types.md の「参照型」を読む。

## 7. エクスポートとインポート・API

- 管理画面のフィールド定義から JSON でエクスポート・インポートできる。インポートは衝突時の扱い（中止・上書き・飛ばす）を選び、確認してから適用する。
- ブログのエクスポート・インポートにも定義が含まれる（ID は取り込み時に読み替えられる）。
- REST API でも読み書きできる（読み取りは `field-definitions:read` か汎用の `read`、書き込みは専用の `field-definitions:write`）。外部から変更するときは acms-rest-api の安全の決まり（dry-run、本番の前に検証）に従う。

## 8. プラグインから拡張する

独自の型・表示場所・表示条件の追加、保存前の値の加工、定義の加工は references/plugin-extension.md を読む。

## よくある誤り

- 3.2 のサイトで定義の JSON を置いて「入力欄が出ない」（Ver. 3.3 から）。
- 編集画面を上書きしたテーマで、定義の入力欄が出ないまま公開時に必須の項目が保存を止める。
- field.html と同じキーで定義を作り、定義側の設定（必須・条件）が効かないと思い込む（field.html が優先される）。
- 中身のある項目の型を変えて、既存の値が読めなくなる。
- エントリーの ID を text の項目に入れ、非公開になった参照先へのリンクが出たままになる（参照型を使う）。
- 選択系の出力に label が出ると思い込む（value が出る）。
- テーマの宣言ファイルを YAML で書く（JSON だけ）。宣言ファイルの壊れた部分は警告ログを残して黙って捨てられるので、入力欄が出ないときは監査ログを見る。
- テーマ由来の定義を管理画面で直そうとする（編集できない。JSON を直すか「使わない」にする）。
