# 大規模サイトの設計と運用

子ブログやカテゴリーが多いサイト、複数人で作るサイト、開発環境と本番環境を分けるサイトで、構成・設定の移行・キャッシュ・性能を判断するときに読む。仕様は Ver. 3.2.38 の本体で確かめたもの。

## 子ブログにするか、カテゴリーにするか

| 違い | 子ブログ | カテゴリー |
|---|---|---|
| 権限 | ユーザーはどれか 1 つのブログに所属し、そのブログを管理する（「子ブログにも権限を与える」なら下の階層のブログも）。ロールもブログ単位で割り当てる | カテゴリー単位の権限は無い。承認ワークフローだけは、エンタープライズ版でカテゴリーごとに設定できる |
| URL | `/ブログコード/`。ブログごとにドメインも持てる | `/ブログコード/カテゴリーコード/` |
| テーマ | ブログ編集でテーマセットを選ぶ | カテゴリー編集でもテーマセットを選べる（ブログより優先） |
| コンフィグ | ブログごと | カテゴリーでもコンフィグセットを選べる |
| ルール | ブログごと | 持たない（ルールの条件にカテゴリーを使う） |
| モジュール ID・フォーム ID | ブログごとに作る | 持たない（ブログの ID を使う） |
| 一覧の範囲 | 一覧系のモジュールは、既定では表示中のブログのエントリーだけを出す | 同じブログの中 |
| 入力欄（カスタムフィールド） | テーマが違えば `admin/entry/field.html` も別にできる | `%{CCD}` 入りのインクルードかテーマセットで出し分ける（acms-custom-field） |
| 移行の単位 | ブログ単位で書き出せる | カテゴリー単位の書き出しは無い |

判断の目安:
- 担当者ごとに管理できる範囲を分けたい、ドメインを分けたい、コンフィグ・モジュール ID・フォームを独立させたい → 子ブログ。
- 同じ担当者・同じ設定で、エントリーを分類したいだけ → カテゴリー。
- 子ブログは、ブログごとにコンフィグ・モジュール ID・フォーム ID が要る。数が多いなら、次の「下の階層のブログと共有する」設定で共通部分を親にまとめる前提で設計する。

## 下の階層のブログと共有する設定

| もの | 親ブログ側の設定 | 子孫のブログでの挙動 |
|---|---|---|
| テーマセット・コンフィグセット・編集画面セット | ブログ編集の「子ブログにも継承する」 | 自分のセットを選んでいない子孫のブログで使われる |
| モジュール ID | 「下の階層のブログが利用することを許可する」 | 子孫のブログのテンプレートから使える。重複の制約は acms-module-reference の references/module-id.md |
| フォーム ID | 同上 | 子孫のブログから使える。同じ名前の制約はモジュール ID と同じ（ローカルは自分のブログと祖先のグローバルと、グローバルは祖先・子孫のすべてと重複できない） |
| ルール | 同上 | 子孫のブログでも条件が評価される |
| カテゴリー | 「下の階層のブログと共有する」 | 子孫のブログの URL（`/子ブログ/カテゴリーコード/`）でも使える |

- どの子ブログでも同じ内容のもの（グローバルナビゲーション、共通フッターなど）は、ルートブログで作ってグローバルにする。子ブログごとに設定を変えたいものは、親ではグローバルにせず、各ブログに同じ名前の ID を作る。
- 子ブログをまたいでエントリーを一覧するときは、モジュール ID を作り、「階層」の「ブログ」を「下階層のブログも含める」にする。ID が無いモジュールや既定のままの ID は、表示中のブログだけが対象（`self`）。

## DB にあるものとファイルにあるもの

| 置き場所 | もの |
|---|---|
| テーマ（ファイル） | テンプレート、`template.yaml`、入力欄の定義（`admin/entry/field.html` など）、テーマの CSS・JavaScript・画像 |
| テーマの外のファイル | `private/config.system.yaml`、`extension/`（プラグイン（拡張アプリ）・Hook）、アップロードされた画像・ファイル（`archives/` など） |
| DB | ブログ・カテゴリー・エントリー・ユニット・ユーザー、カスタムフィールドの値、テーマセット・コンフィグセット・編集画面セットとその中身、どのブログ・カテゴリーがどのセットを選んでいるか、ルール、モジュール ID、フォーム ID、メディアの情報 |

- テーマを Git で共有しても、DB にあるものは運ばれない。テンプレートに書いたモジュール ID・フォーム ID は、各環境の DB にあるかを確かめる（無くてもエラーにならない）。
- `config.server.php` は環境ごとの DB 接続情報を持つ。エージェントは読まず、環境間でコピーもしない。

## 設定とデータを運ぶ機能

| 機能 | 単位 | 運ぶもの | 運ばないもの | インポート先での挙動 |
|---|---|---|---|---|
| データベースのバックアップ・リストア | サイト全体 | アクセスログとキャッシュ以外のテーブル | アップロードされたファイル（アーカイブのエクスポートは別） | DB 全体を置き換える |
| ブログのエクスポート・インポート | ブログ | カテゴリー、エントリー（ゴミ箱を除く）、ユニット、タグ、カスタムフィールド、メディアとファイル、コンフィグ、セット、ルール、モジュール ID、フォーム ID など | ユーザー、エントリーの履歴（リビジョン） | インポートしたブログの既存のエントリー・カテゴリー・設定を消して置き換える |
| コンフィグのエクスポート・インポート | ブログ | そのブログのセット（テーマセット・編集画面セットを含む）とその中身、ルール、モジュール ID とモジュールフィールド | フォーム ID、どのブログ・カテゴリーがどのセットを選んでいるか、バナーの中身、モジュールフィールドの画像・ファイル | そのブログのセット・コンフィグ・ルール・モジュール ID を消してから入れる（足し合わせない） |
| コンフィグの部分エクスポート・インポート | コンフィグの画面 1 つ | その画面の項目 | ― | ファイルにある項目だけ上書きする |
| モジュール ID のエクスポート・インポート | ID 1 件 | ID の設定とモジュールフィールド | ― | 同じブログに同じ名前の ID があれば置き換える |
| フォームのエクスポート・インポート（Ver. 3.2.25 以降） | フォーム ID 1 件 | フォームの設定 | 投稿データ | 同じブログに同じフォーム ID があれば上書き、無ければ追加 |
| コンフィグセットのエクスポート・インポート（Ver. 3.2.29 以降） | セット 1 件 | セットの設定値 | ルールごとの上書き | 新しく作るか、選んだセットを上書きする |

コンフィグのインポートで起きること（よくある誤りの元）:
- セット・ルール・モジュール ID には新しい ID が振られる。モジュール ID やルールに設定したカテゴリー・エントリー・ユーザーなどは、コード（カテゴリーコードなど）でインポート先の ID に置き換えられ、見つからなければ空になってレポートに出る。
- ブログ・カテゴリーがどのセットを選んでいるかは運ばれず、書き換えもされない。インポートの後は、ブログ編集・カテゴリー編集でテーマセット・コンフィグセット・編集画面セットの選択が意図どおりかを確かめる。
- 祖先のブログに同じ名前のグローバルなモジュール ID がある、またはグローバルにする ID と同じ名前の ID が子孫のブログにある場合、その ID はインポートされずレポートに出る。インポート後は必ずレポートを読む。
- 本番で直接変えたコンフィグ・モジュール ID は、次に開発環境から丸ごとインポートすると消える。どちらの環境で設定を作るかを決めておく。
- フォームのインポートは、祖先・子孫のブログにある同じ名前のグローバルなフォーム ID との重複を確かめない（Ver. 3.2.38）。グローバルにしたフォーム ID と同じ名前のものを子ブログに入れない。

## 開発環境から本番環境へ反映する

- 公開前で本番に残すデータが無いときは、データベースのバックアップ・リストアとファイルのコピーで丸ごと移してよい。手順（ドメインの修正を含む）は「テスト環境を本番へ反映する」のページを見る。
- **公開後は、本番の DB を開発環境の DB で上書きしない。** リストアやブログのインポートは、本番で増えたエントリー・ユーザー・フォームの投稿データ・アップロードされたファイルの情報を置き換えて失う。
- 公開後の反映は、テーマはファイルで、設定は上の表の個別の機能（モジュール ID・フォーム・コンフィグセット・部分エクスポート）で運ぶ。ブログ全体のコンフィグのインポートは、そのブログの設定を丸ごと入れ替えてよいときだけ使う。
- インポートする前に、本番側の同じものをエクスポートして控えておく（上の表のとおり、インポートは既存のものを上書き・置き換えする）。
- テンプレートを本番に置いたら、テンプレートキャッシュとページキャッシュをクリアする（下の「キャッシュ」）。
- エージェントは本番の管理画面の操作・DB の操作をしない。手順と確認項目を示し、利用者に実行してもらう。

## キャッシュ

| キャッシュ | 中身 | 使われる条件 | 消える条件 |
|---|---|---|---|
| ページキャッシュ | ページの HTML（URL と、そのページで適用されたルールごと） | キャッシュ設定が有効、ログアウト中（読者は設定次第）、GET で 200 のページ、デバッグモードでない | 有効時間が過ぎる、更新の操作（エントリー保存・設定の保存など）のとき「キャッシュクリアの対象ブログ」に従って消える（「POST 時のキャッシュクリア」が有効なとき）、エントリーの更新でそのエントリーのページ、ダッシュボードのキャッシュクリア |
| モジュールキャッシュ | モジュール ID ごとの結果 | ID にキャッシュ時間を入れ、ログアウト中 | 有効時間が過ぎる、ダッシュボードのキャッシュクリア。キーにブログ・URL を含まないなどの注意は acms-module-reference の references/module-id.md |
| テンプレートキャッシュ | 組み立て済みのテンプレート（テンプレートのパス・テーマ・`%{BCD}`・`%{CCD}` などの組ごと） | `template_cache` が on（新規インストールの `config.system.yaml` は on）、デバッグモードでない | ダッシュボードのキャッシュクリア（Twig のコンパイル済みキャッシュも一緒に消える）、本体のアップデート、有効期限。**テンプレートのファイルを書き換えても消えない** |

- ページキャッシュが当たると、テンプレートもモジュールも処理されない。テンプレートを直してテンプレートキャッシュだけ消しても、ページキャッシュが残っていれば古いページが出る。両方消す。
- 「キャッシュクリアの対象ブログ」の既定は「全ブログ」。子ブログが多いと、どこかでエントリーを保存するたびにサイト全体のページキャッシュが消え、キャッシュが効きにくくなる。子ブログの内容を親ブログ（トップページの新着一覧など）で出しているなら「実行ブログと親階層のブログ」、出していないなら「実行ブログのみ」のように、サイトの構成に合わせて選ぶ。「実行ブログのみ」にすると、親ブログの一覧は有効時間が過ぎるまで古いまま残る。
- ダッシュボードのキャッシュクリアは、編集者以上ならどのブログのダッシュボードからでもできる（Ver. 3.2.38 のソース）。ページキャッシュはそのブログの「キャッシュクリアの対象ブログ」に従い、テンプレート・モジュールなどのキャッシュはブログに関係なく全部消える。
- 「デバッグモード」「デバッグモード & ベンチマークモード」のユーザーでは、ページキャッシュもテンプレートキャッシュも使われない。インストール時に作られる管理者ユーザーはデバッグモードになっている。本番で起きる表示の違い（テンプレートキャッシュによるもの）は、通常モードのユーザーかログアウトした状態で確かめる。

## 重いページを特定する

1. 管理者ユーザーのモードを「デバッグモード & ベンチマークモード」にしてもらい、対象ページを開く。ページ下部にモジュールごとの処理時間と SQL の数が出る。
2. ログイン中はページキャッシュもモジュールキャッシュも使われないので、出る数字はキャッシュが無いときの重さ（キャッシュが消えた直後の閲覧者が待つ時間）になる。
3. 重いモジュールが分かったら、次を見直す。
   - エントリーの本文が要らない一覧に `Entry_Body` を使っていないか（一覧は `Entry_Summary`。acms-module-reference）。
   - 件数。ページャー（全件数）を使わない一覧では、モジュール ID の表示設定でページャーを無効にする。有効なときだけ全件数を数える SQL が走る。
   - 使わない表示項目（関連エントリー・カスタムフィールドなど）が有効になっていないか。
   - どのページでも同じ内容のモジュールなら、モジュール ID のキャッシュを使えるか。
4. 終わったらモードを元に戻してもらう。

## 複数人での開発

- 土台のテーマとブログごとの子テーマに分け（SKILL.md の推奨）、子テーマには差分だけを置く。担当するブログの子テーマを分けると、作業が重なりにくい。
- `themes/system` と本体のファイルを直さない（アップデートで上書きされる。SKILL.md）。
- テーマのディレクトリは Web からそのまま見える場所にある（配布物の `themes/htaccess.txt` が拒否するのは `.html`・`.htm`・`.xml` だけ）。ビルドの元のファイル（`node_modules/`・ソース）はテーマの外に置き、テーマにはビルドした成果物だけを置く。
- 開発環境では、デバッグモードのユーザーならテンプレートの変更がすぐ反映される。本番や通常モードのユーザーではテンプレートキャッシュのクリアが要る。「自分の環境では反映されているのに本番で変わらない」ときは、まずキャッシュを疑う。
- モジュール ID・フォーム ID・コンフィグなど DB の設定は Git で共有できない。どの環境で作り、どの機能（上の表）で他の環境へ運ぶかを決めておく。

## 権限・承認・会員機能（どれを選ぶか）

| したいこと | 使う機能 | ドキュメント |
|---|---|---|
| 担当者ごとに管理できる範囲を分ける | 子ブログとユーザーの所属ブログ。権限の中身を細かく決めるならロール（エンタープライズ版） | <https://developer.a-blogcms.jp/document/enterprise/entry-2553.html> |
| 公開の前に承認を挟む | 承認機能（プロフェッショナル版はコンフィグの機能設定で有効にする。エンタープライズ版はブログ・カテゴリーごとにワークフローを設定する） | <https://developer.a-blogcms.jp/document/professional/entry-2584.html>、<https://developer.a-blogcms.jp/document/enterprise/entry-3242.html> |
| 同じエントリーを同時に編集させない | 編集ロック（プロフェッショナル版） | <https://developer.a-blogcms.jp/document/professional/entry-3979.html> |
| 会員だけが見られるページを作る | 会員機能 | <https://developer.a-blogcms.jp/document/auth/Introduction.html> |

ライセンスの種類で使える機能が違う。利用者のライセンスを確かめてから提案する。
