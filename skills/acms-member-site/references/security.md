# 会員制サイトのセキュリティ上の注意（a-blog cms の挙動に由来するもの）

ページキャッシュの設定を決めるとき、会員ごとの値をページに出すとき、会員の情報を保存する項目を設計するとき、「ログアウトしても見える」「他人の名前が出る」と相談されたときに読む。

## ページキャッシュとログイン状態

本体のページキャッシュは次の条件で使われる（v3.2.38 のソースで確認）。

| 状態 | ページキャッシュ | ブラウザ・CDN への指示 |
|---|---|---|
| 未ログイン | 使う（シークレットのブログ・カテゴリーを除く） | キャッシュ設定のクライアントキャッシュの時間に従う |
| ログイン中（読者以外） | 使わない | 保存させない（no-store） |
| ログイン中の読者で「読者ユーザーの場合」が無効（既定） | 使わない | 保存させない |
| ログイン中の読者で「読者ユーザーの場合」が有効 | **使う。キーに会員の区別は無く、全読者で共有する** | 保存させない |

- 認証系の画面とマイページ系の画面は、設定にかかわらずページキャッシュを使わない。
- 「読者ユーザーの場合」を有効にすると、`%{SESSION_USER_NAME}` や `Member_Update_Profile` の値、`Touch_Login` の中身などを、最初にそのページを開いた読者の内容のまま他の読者へ返す。有効にするなら:
  - 会員ごとの値をページに直接書かない。member テーマのヘッダーのように、`ACMS_POST_2GET_Ajax` で `nocache=yes` を付けて部品を後から読み込む（Ajax のリクエストに `nocache=yes` を付けると、ページキャッシュを使わない。本体の設定 `ajax_nocache` が既定の有効のとき）。
  - ログイン状態での出し分けは組み込み JS（`js-login-show` など）にする。
  - 会員ごとに内容が変わるページ（マイページのトップなど）は、そのページだけキャッシュを無効にする。
- **Ver. 3.2.37 以前**は、読者向けに作ったページキャッシュと未ログイン向けのキャッシュのキーが同じだった。「読者ユーザーの場合」が有効だと、読者が開いたシークレットのページや Touch_Login の中身が、未ログインの訪問者にも返りうる。Ver. 3.2.38 でキーが分かれ、シークレットのブログ・カテゴリーは未ログイン向けにキャッシュしなくなった。3.2.37 以前のサイトでは「読者ユーザーの場合」を無効にし、キャッシュを消してもらう（または 3.2.38 以降に上げる）。
- 「ログアウトしても会員限定のページが見える」と言われたら、次の順に確かめる。
  1. 本当に会員限定にしているか（ブログ・カテゴリーのステータス、子カテゴリー、会員限定記事のバー。references/members-only.md）。
  2. 内容を `js-login-show` や CSS で隠しているだけではないか（HTML には含まれている）。
  3. 「読者ユーザーの場合」のページキャッシュが有効で、バージョンが 3.2.37 以前ではないか。
  4. 一覧の抜粋・OGP の description・検索結果・Unit_List から見えているのではないか。
  5. 設定を直した後に、ページキャッシュを消したか。

## 会員ごとの値を出すときのエスケープ

- 標準テンプレートの `{変数}` と Twig の `{{ }}` は既定でエスケープされる。会員が入力した値（名前・プロフィール・自由記入欄）には `[raw]` / `|raw` を付けない。改行を出すなら `[nl2br]` / `|nl2br` だけにする。
- `%{SESSION_USER_NAME}` などのグローバル変数は、本体が HTML のエスケープをしてから埋め込む。
- 自分の情報は `Member_Update_Profile` で出す。User_Field は URL の uid で対象のユーザーが決まり、ステータスが「無効」でない限り誰の値でも出す。User_Search の既定の対象は読者で、会員登録したユーザーは検索の対象（インデックス）に入る。会員の個人情報をユーザーのカスタムフィールドに置くサイトでは、これらを公開側に置かない。置くなら出す項目と対象の権限を絞る。

## 会員が書き換えられる値

- 会員登録とプロフィール変更は、送られてきた `field[]` の項目をそのままユーザーのカスタムフィールドに保存する（プロフィール変更は送られた項目だけを置き換える）。テンプレートに無い項目名でも、POST を作れば保存できる。
- 有料会員かどうか・会員種別・管理用のメモなど、会員に変えさせたくない値をユーザーのカスタムフィールドに置かない。置く必要があるなら、管理画面でだけ入力し、表示や判定に使わない。権限の判定はユーザーの権限（読者・投稿者など）で行う。
- 基本の項目（`user[]`）で会員が変えられるのは、名前・ユーザーコード・URL・メールマガジンの受信・アイコンなどに限られ、権限やステータスは変えられない。

## メール

- パスワード再設定・会員登録の確認・メールアドレス変更のメールには、本体が作る認証用の URL（`{authUrl}`・`{subscribeUrl}` など）が入る。テンプレートを作り直すときもこの変数を残す。system テーマのテンプレートは、テキストのメールでも HTML のメールでもこの URL に `[raw]` を付けている。
- リンクには有効時間がある（パスワード変更の有効時間・確認メールの有効時間）。パスワード再設定のリンクは、同じアドレスで再発行すると前のリンクが無効になり、1 回しか使えない（Ver. 3.2.29 以降）。
- パスワード再設定は、登録の無いメールアドレスでも同じ応答を返し、応答時間もそろえる（Ver. 3.2.29 以降）。テンプレートで登録の有無を出し分けない。
- メールの送信元（From）の既定値は `info@example.com`。利用者に自サイトのドメインのアドレスへ変えてもらう。

## ログイン試行の制限など本体にある仕組み

- アカウントロック: ログイン設定のアカウントロック（既定は 5 分間に 5 回失敗で 5 分間）。サインインの画面で `{mail:validator#lock}` のときに `{trialNumber}`・`{lockTime}` を使って案内する。2段階認証のコードも同じ制限を受ける。
- 一般サインイン制限（アクセス設定）: 会員の認証の画面を開ける IP アドレスを限る。許可外は 404。
- パスワードポリシー: 会員登録・パスワード変更・再設定で本体が検証する（`{pass:validator#password}`）。
- CSRF: 本体が `</form>` の直前にトークンを入れる。フォームの閉じタグを JavaScript で作ると入らない（acms-form と同じ）。トークン切れ・二重送信・不正なアクセスは `SystemError` モジュールの `CsrfTokenExpired`・`DoubleTransmission`・`IllegalAccess` などで表示できる（member テーマの `_member/parts/error.html`）。
- 管理ログインと一般サインインは画面も権限も分かれている。会員制サイトで管理者が一般サインインの画面からログインできないのは仕様。

## 退会

- 退会は会員本人が `ACMS_POST_Member_Withdrawal` で行う。管理ログイン側の権限のユーザーと、エントリーを持つユーザーは退会できない。
- 削除タイプが「論理削除」なら、データ保存期間が過ぎるまで情報が残る。個人情報の扱いの方針に合わせて利用者に決めてもらう。
